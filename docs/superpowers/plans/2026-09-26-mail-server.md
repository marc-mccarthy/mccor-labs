# Mail Server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring `infra/modules/mailserver` up to the approved spec so four
people have real mailboxes on mccorlabs.com, on one EC2 instance, for
~$20/month flat.

**Architecture:** One `t4g.small` Debian ARM instance running
docker-mailserver in Docker, receiving SMTP directly on port 25 and
relaying outbound through SES on 587. Mail lives on a separate encrypted
EBS volume snapshotted every 6 hours by DLM. Mailbox passwords are
generated by Terraform into SSM SecureString and read at boot, so adding a
person never replaces the instance. Nine free CloudWatch/Route53 alarms
report to an SNS topic.

**Tech Stack:** Terraform ~> 1.16, AWS provider ~> 6.58, random ~> 3.6,
Debian 13 ARM64, Docker, docker-mailserver (pinned tag), certbot, SSM
Session Manager, DLM, SES.

**Spec:** `docs/superpowers/specs/2026-09-26-mail-server-design.md`

## Global Constraints

- Terraform `~> 1.16`; AWS provider `~> 6.58`; random `~> 3.6`.
- Region `us-east-1`. Account `150701180133`. Domain `mccorlabs.com`.
- Run every `terraform` command with `dangerouslyDisableSandbox: true` —
  the sandbox's TLS interception breaks the provider registry with
  `x509: OSStatus -26276`.
- Use `AWS_PROFILE=default`. There is no `terraform` profile.
- **Credentials fail roughly 1 in 3 calls** with `No valid credential
sources found` or `authorization timeout` from a custom
  `credential_process`. Retry up to 4 times before treating it as real.
  Never report a credential flake as a config error.
- `terraform fmt -recursive` must pass before every commit.
- Module files are `main.tf` / `variables.tf` / `outputs.tf`; comments
  explain _why_, not _what_.
- Names: keep dots for Name tags, Route53, SES identities and SSM paths;
  `replace(domain, ".", "-")` for S3, IAM, Lambda and log groups.
- No secret is ever a variable or a non-sensitive output.
- **Never run `terraform apply` without the user's explicit go-ahead for
  that specific apply.** Plans are free; applies cost money and create
  real mail infrastructure.

## Review Focus

Five conditions the spec implies that no single task's checks exercise.
Each has a test pinned to the task that owns the code.

1. **Adding a fifth mailbox must not replace the instance.** The whole
   point of Task 4. Pinned to Task 4, Step 6 — a plan diff asserting
   `0 to change, 0 to destroy` on the instance after adding a mailbox.
2. **A second `apply` with no edits must be a no-op.** Drift from
   `most_recent` AMI lookups or computed attributes shows up here. Pinned
   to Task 10, Step 3.
3. **An empty `alert_email` or `domain_name` must fail fast**, not deploy
   a placeholder. Pinned to Task 1, Step 4.
4. **`admin_mailbox` naming a nonexistent mailbox must fail validation**,
   or postmaster mail silently vanishes. Pinned to Task 1, Step 5.
5. **`terraform destroy` must not be blocked by a flag we set**, and must
   leave only the documented survivors. Pinned to Task 11, Step 2.

  # the host itself, so a container's request is dropped. Without this,

**Interfaces:**

- Produces: a template variable `mail_device` holding the Nitro by-id path.

- [ ] **Step 1: Pin the volume's availability zone**

In `aws_ebs_volume.mail`, replace
`availability_zone = aws_instance.mail.availability_zone` with:

```hcl

  # instance replacement the instance's AZ becomes "known after apply",
  # which forces replacement of this volume -- and availability_zone is
  # ForceNew, so that is data loss. Do not "simplify" this line.

```

- [ ] **Step 2: Pass the by-id path into the template**

In `aws_instance.mail`'s `templatefile` map, add:

```hcl

```

- [ ] **Step 3: Replace the detection loop**

In `setup.sh.tftpl`, replace the whole `for i in $(seq 1 30)` block and the
`if [ -n "$DEV" ]` block with:

```bash
# ---------- mail disk ----------
# Nitro exposes a stable symlink per volume, so the disk is identified
# exactly rather than guessed at by size. The old guess could select
# nothing, letting mkdir succeed on the root volume and mail accumulate
# somewhere that is never backed up.
DEV="${mail_device}"
for i in $(seq 1 12); do
  [ -e "$DEV" ] && break
  sleep 5
done

if [ ! -e "$DEV" ]; then
  echo "FATAL: mail volume $DEV never appeared" >&2
  exit 1
fi

# Only format a genuinely empty disk. A restored snapshot already has a
# filesystem and must not be touched.
blkid "$DEV" >/dev/null 2>&1 || mkfs.ext4 -L maildata "$DEV"

mkdir -p /var/mail-data
# Mount by LABEL, not by ID: a volume restored from a snapshot gets a new
# volume ID but keeps its label.
grep -q maildata /etc/fstab || echo "LABEL=maildata /var/mail-data ext4 defaults,nofail 0 2" >> /etc/fstab
mount -a

if ! mountpoint -q /var/mail-data; then
  echo "FATAL: /var/mail-data did not mount" >&2
  exit 1
fi

mkdir -p /var/mail-data/{mail-data,mail-state,mail-logs,config,letsencrypt}
```

```bash

# Mailboxes are read from Parameter Store at run time rather than baked
# into user-data. Templating them in would mean every new hire replaces
# the instance, since user_data_replace_on_change is set.
cat > /opt/mail/sync-accounts.sh <<SYNC
#!/usr/bin/env bash
# Creates any mailbox that exists in Parameter Store but not yet on this
# server. Safe to re-run. Never deletes: removing someone is deliberate.
set -euo pipefail

aws ssm get-parameters-by-path --region ${region} --path ${param_prefix} \\
    --with-decryption --query 'Parameters[].[Name,Value]' --output text |

  ADDR="\\\$LOCAL@${domain}"
  if docker exec mailserver setup email list 2>/dev/null | grep -q "^\\* \\\$ADDR"; then
    continue
  fi
  echo "creating \\\$ADDR"
  docker exec mailserver setup email add "\\\$ADDR" "\\\$PASS"
done
SYNC
chmod +x /opt/mail/sync-accounts.sh
/opt/mail/sync-accounts.sh
```

## Task 5: Certificates on the persistent volume

Let's Encrypt allows 5 certificates per name set per 7 days. With the ACME
store on the disposable root volume, six boot-script edits in a week locks
issuance for 34+ hours.

**Files:**

- Modify: `infra/modules/mailserver/templates/setup.sh.tftpl` (certbot
  section and the compose volume list)

**Interfaces:**

- Consumes: `/var/mail-data` mounted by Task 3.
- Produces: certificates under `/var/mail-data/letsencrypt`.

- [ ] **Step 1: Point certbot at the persistent volume**

Replace the certbot block with:

```bash
# ---------- TLS certificate ----------
# The ACME store lives on the MAIL volume, not the root volume. Let's
# Encrypt allows 5 certificates per name set per week; with the store on
# the disposable root disk, a handful of instance replacements locks
# issuance for over a day. On the mail volume a rebuilt instance finds
# its existing certificate and issues nothing.
apt-get install -y certbot
ln -sfn /var/mail-data/letsencrypt /etc/letsencrypt

if [ ! -d "/etc/letsencrypt/live/$FQDN" ]; then
  for i in $(seq 1 20); do
    certbot certonly --standalone --non-interactive --agree-tos \
      -m "$ALERT_EMAIL" -d "$FQDN" && break
    echo "certbot failed (DNS may not have propagated); retrying in 60s"
    sleep 60
  done
fi

if [ ! -d "/etc/letsencrypt/live/$FQDN" ]; then
  echo "FATAL: no certificate for $FQDN" >&2
  exit 1
fi
```

- [ ] **Step 2: Add a renewal hook that reloads the mail server**

# Webmail (v2) Implementation Plan

> Queued after the mail server's first successful apply. Do NOT start this
> until mail is confirmed working end to end — the whole approach depends on
> having a running box to iterate against.

**Goal:** A browser inbox at `https://mail.mccorlabs.com`, same credentials as
IMAP, on the existing instance, for $0 extra per month.

**Spec:** `docs/superpowers/specs/2026-09-26-mail-server-design.md` — the
"What v1 is, and is not" section records why this was deferred and what shape
it should take.

## Prerequisite — do not skip

Mail must be working first: a real message sent from an external account to a
mailbox and read in an IMAP client, and a reply delivered back. If that has
not happened, stop. Debugging webmail on top of unproven mail means two
unknowns at once.

## Global Constraints

- Terraform `~> 1.16`, AWS provider `~> 6.58`, us-east-1, domain mccorlabs.com.
- Run every terraform command with `dangerouslyDisableSandbox: true` — the
  sandbox's TLS interception breaks the provider registry.
- `AWS_PROFILE=default`. Credentials on this machine are intermittent; retry
  up to 4 times before treating a failure as real.
- `terraform fmt -recursive` before every commit.
- **certbot keeps owning ACME.** Do not introduce a second ACME client. Caddy
  reads certbot's existing certificates from
  `/var/mail-data/letsencrypt/live/mail.mccorlabs.com/`.
- **Never put `mem_limit` on the docker-mailserver container.** It is the thing
  that must survive. A PHP runaway must not be able to OOM Postfix.
- Roundcube's container must NOT mount the maildir. It reaches mail over IMAP
  like any other client.
- No `terraform apply` without the user's explicit go-ahead.

## The approach, and why

Everything here lives in the instance's user-data, so a mistake costs an
instance replacement to retest. Rather than guess, **iterate live on the
running box first, then codify what works.** Tasks 1 and 2 are deliberately
in that order.

An instance replacement is safe by design: the mail volume, the mailboxes and
the certificates all survive it, because they live on the separate encrypted
volume. Expect a ~10 minute gap during which senders queue and retry.

## Task 1: Make it work by hand on the running box

No Terraform yet. The deliverable is a working configuration on disk that you
have seen serve a real inbox.

- [ ] **Step 1: Get on the box**

```bash
cd /Users/mj/repos/mccor-labs/infra/setup
aws ssm start-session --target "$(terraform output -raw mail_instance_id)"
sudo -i
```

- [ ] **Step 2: Create the webmail data directory on the PERSISTENT volume**

```bash
mkdir -p /var/mail-data/webmail /var/mail-data/caddy
chown -R 1000:1000 /var/mail-data/webmail
```

It must be under `/var/mail-data` — that is the volume DLM snapshots. On the
container's own layer it would be wiped by every weekly image update.

- [ ] **Step 3: Write the Caddyfile**

`/opt/mail/Caddyfile`:

```
mail.mccorlabs.com {
    # certbot owns ACME; Caddy only terminates TLS with what certbot issued.
    tls /etc/letsencrypt/live/mail.mccorlabs.com/fullchain.pem /etc/letsencrypt/live/mail.mccorlabs.com/privkey.pem

    encode gzip

    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        X-Content-Type-Options    "nosniff"
        X-Frame-Options           "DENY"
        Referrer-Policy           "strict-origin-when-cross-origin"
        -Server
    }

    # Roundcube's login endpoint is the brute-force target. fail2ban bans
    # repeat offenders; this blunts fast bursts before they get that far.
    @login path /index.php
    rate_limit @login {
        zone login {
            key    {remote_host}
            events 20
            window 1m
        }
    }

    reverse_proxy roundcube:80 {
        # Without this Roundcube logs the proxy's IP, and the fail2ban jail
        # then bans nobody -- or bans every user on one bad login.
        header_up X-Forwarded-For {remote_host}
        header_up X-Real-IP       {remote_host}
    }
}
```

- [ ] **Step 4: Add the two services to the compose file**

Append to `/opt/mail/compose.yaml`. Note for Task 2: in the boot script this
file is written with an UNQUOTED heredoc (`cat > compose.yaml <<COMPOSE`),
because it needs `$FQDN`, `$RELAY_USER` and `$RELAY_PASSWORD` expanded at
write time. So anything you add there must contain no unintended `$` or
backticks — they will be expanded by bash before the file is written.

```yaml
roundcube:
  image: roundcube/roundcubemail:latest
  container_name: roundcube
  restart: always
  depends_on: [mailserver]
  volumes:
    - /var/mail-data/webmail:/var/roundcube/db
  environment:
    - ROUNDCUBEMAIL_DEFAULT_HOST=tls://mailserver
    - ROUNDCUBEMAIL_DEFAULT_PORT=143
    - ROUNDCUBEMAIL_SMTP_SERVER=tls://mailserver
    - ROUNDCUBEMAIL_SMTP_PORT=587
    - ROUNDCUBEMAIL_DB_TYPE=sqlite
    - ROUNDCUBEMAIL_DB_DIR=/var/roundcube/db
    - ROUNDCUBEMAIL_PLUGINS=archive,zipdownload
    - ROUNDCUBEMAIL_UPLOAD_MAX_FILESIZE=25M
  # Capped so a PHP runaway cannot take Postfix down with it.
  mem_limit: 400m

caddy:
  image: caddy:2-alpine
  container_name: caddy
  restart: always
  depends_on: [roundcube]
  ports:
    - '443:443'
  volumes:
    - /opt/mail/Caddyfile:/etc/caddy/Caddyfile:ro
    # Same mount point the mailserver container already uses for these
    # certs, so both containers refer to one path. certbot writes them to
    # /var/mail-data/letsencrypt on the host.
    - /var/mail-data/letsencrypt:/etc/letsencrypt:ro
    - /var/mail-data/caddy:/data
  mem_limit: 100m
```

`ROUNDCUBEMAIL_PLUGINS` is deliberately short — every enabled plugin is more
code with its own CVE surface.

- [ ] **Step 5: Bring it up and watch**

```bash
cd /opt/mail
docker compose up -d roundcube caddy
docker compose logs -f caddy roundcube
```

- [ ] **Step 6: Prove it in a browser**

Open `https://mail.mccorlabs.com`, sign in as `marcm@mccorlabs.com` with the
password from `terraform output -json mailbox_passwords`. Send a message, read
one, confirm the certificate is valid and not self-signed.

**Do not proceed until this works.** Iterate here — it costs seconds, whereas
the same mistake in user-data costs an instance rebuild.

- [ ] **Step 7: Remove the installer**

```bash
docker exec roundcube rm -rf /var/www/html/installer
```

A reachable `/installer/` is a classic pre-auth compromise path.

- [ ] **Step 8: Save what worked**

Copy the final `Caddyfile` and the compose additions off the box. They are the
input to Task 2.

## Task 2: Codify it into Terraform

**Files:**

- Modify: `infra/modules/mailserver/templates/setup.sh.tftpl`
- Modify: `infra/modules/mailserver/main.tf` (443 ingress rule)
- Modify: `infra/modules/mailserver/variables.tf` (`enable_webmail`)
- Modify: `infra/settings.auto.tfvars` and `.example`

- [ ] **Step 1: Add the variable**

```hcl
variable "enable_webmail" {
  description = "Serve Roundcube at https://<hostname>. Adds a public login page, which is the most-attacked surface on the box -- only turn this on if the weekly image update in the boot script is left in place."
  type        = bool
  default     = false
}
```

- [ ] **Step 2: Open 443, conditionally**

`aws_vpc_security_group_ingress_rule.mail`'s `for_each` is currently a PLAIN
MAP LITERAL (verified at `infra/modules/mailserver/main.tf`), not a `merge()`
call — so it has to be wrapped, not appended to:

```hcl
  for_each = merge({
    smtp       = { port = 25, note = "inbound mail from other servers" }
    http       = { port = 80, note = "Let's Encrypt renewal" }
    submission = { port = 587, note = "your people sending (STARTTLS)" }
    imaps      = { port = 993, note = "your people reading" }
    }, var.enable_webmail ? {
    https = { port = 443, note = "webmail" }
  } : {})
```

Do not add a second `aws_vpc_security_group_ingress_rule` resource — the four
existing rules are keyed by this map, and splitting them would make the keys
inconsistent.

- [ ] **Step 3: Write the config from the boot script**

Add the Caddyfile heredoc and the compose services, both gated on
`enable_webmail`. Use a QUOTED heredoc delimiter (`<<'CADDY'`) — the Caddyfile
contains `{remote_host}` and `{...}` blocks that Terraform would otherwise try
to interpret, and bash would mangle. This is the same trap Task 4 of the mail
plan hit.

**Terraform parses `${...}` even inside `#` comments.** Escape as `$${...}`.

- [ ] **Step 4: Extend the certbot renewal hook**

The existing deploy hook restarts the mail container. Caddy holds the cert
files open too:

```bash
docker restart mailserver caddy 2>/dev/null || true
```

- [ ] **Step 5: Verify without applying**

```bash
cd /Users/mj/repos/mccor-labs/infra
sed -e 's/\${[a-z_]*}/x/g' modules/mailserver/templates/setup.sh.tftpl > "$TMPDIR/r.sh"
bash -n "$TMPDIR/r.sh" && echo "SHELL SYNTAX OK"
terraform fmt -recursive && terraform -chdir=setup validate
```

Then plan with the backend file moved aside (the method in `MAIL.md`), and
confirm the only new resource is the 443 ingress rule.

- [ ] **Step 6: Commit**

## Task 3: Harden it

- [ ] **Step 1: fail2ban jail for Roundcube**

Roundcube logs auth failures with the client IP **only if** `X-Forwarded-For`
is wired through, which Task 1 Step 3 does. Verify before trusting the jail:
make three bad logins and confirm the log shows your real IP, not the
container's gateway.

Add a jail watching Roundcube's log, separate from the existing SMTP/IMAP jails.

- [ ] **Step 2: Confirm the ban actually works**

Trigger it deliberately and confirm you are locked out, then unban yourself:

```bash
docker exec mailserver fail2ban-client status roundcube
docker exec mailserver fail2ban-client set roundcube unbanip <your-ip>
```

A jail that has never been observed banning anyone is not a jail.

- [ ] **Step 3: Session hardening**

`session_lifetime = 30`, `session_samesite = 'Strict'`, and secure cookies —
free, since only 443 is exposed.

## Task 4: The weekly update — non-negotiable

Roundcube's CVE record is the reason this whole component was made
conditional. CVE-2025-49113 was a CVSS 9.9 RCE weaponised within days, with
~85,000 instances still unpatched a week later; CVE-2026-48842 was a pre-auth
SQL injection under active exploitation in September 2026.

**Pin docker-mailserver, auto-update Roundcube.** Those look contradictory and
are not: the mail stack breaks on upgrade and is not internet-facing; the
webmail is under live attack and must stay current.

- [ ] **Step 1: systemd timer**

```
/etc/systemd/system/roundcube-update.service   # docker compose pull roundcube && up -d roundcube
/etc/systemd/system/roundcube-update.timer     # weekly, Sunday 03:00, Persistent=true
```

`Persistent=true` so a missed run fires on next boot.

- [ ] **Step 2: Prove it runs**

```bash
systemctl start roundcube-update.service
systemctl status roundcube-update.service
systemctl list-timers roundcube-update.timer
```

- [ ] **Step 3: Alarm on it failing**

Add to the existing daily health cron: if the Roundcube image is older than
14 days, publish to SNS. An update mechanism nobody checks is the same as none.

## Verification, end to end

- [ ] Browser login works from a device that has never touched this domain
- [ ] Sending from webmail arrives externally, with `dkim=pass header.d=mccorlabs.com`
- [ ] A message sent from an IMAP client appears in webmail, and vice versa
- [ ] Roundcube preferences survive `docker compose down && up -d` (proves the
      SQLite database is on the persistent volume, not the container layer)
- [ ] Preferences survive an image update (the real test of the same thing)
- [ ] fail2ban has been observed banning a real IP
- [ ] `https://` shows a valid certificate, `http://` is not served at all
- [ ] Memory: `free -m` under a webmail session plus mail load leaves headroom;
      if `mem_available_percent` alarms twice in 30 days, move to `t4g.medium`

## Cost

**$0/month extra.** Roundcube and Caddy are containers on an instance you are
already paying for. The only new AWS object is a security group rule, which is
free. The real cost is operational: a weekly image update you must not skip.

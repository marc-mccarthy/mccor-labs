# Fix round 1: `text-base` colour/font-size collision in `size.lg`

## The defect

`app/web/src/components/ui/button.tsx`'s `size.lg` variant was `'h-13 px-8 text-base'`. Tailwind
v4's `@theme` block in `app/web/src/styles/globals.css:7` defines `--color-base: #070a12`, which
makes Tailwind generate `.text-base { color: var(--color-base) }` — a colour utility, not the
built-in font-size utility of the same name. `.text-base`'s generated CSS offset (7156) sorts after
`.text-accent` (7103), so it wins the cascade. Two consequences: `size="lg"` never got its intended
font-size bump, and `variant="link" size="lg"` rendered a `#070a12` label on the `#070a12` page
background (~1:1 contrast — an invisible button).

`variant: primary`'s `'bg-accent text-base hover:bg-brand'` uses `text-base` as a colour
**deliberately** — the comment above it (`// Dark label on the accent fill: 5.31:1.`) documents the
measured contrast pair. That usage is untouched by this fix.

## The fix

`app/web/src/components/ui/button.tsx:18-23`, `size.lg` changed from:

```ts
lg: 'h-13 px-8 text-base',
```

to:

```ts
// text-base resolves to the --color-base colour utility here, not a font
// size, so lg uses an arbitrary value to get the intended size bump.
lg: 'h-13 px-8 text-[1rem]',
```

`text-[1rem]` is an arbitrary length value, not a colour literal, so it does not trip the
`app/web/src/**/*.tsx` ESLint rule banning raw hex/`rgb()`/`hsl()`/`oklch()`. No colour token was
renamed; `globals.css` and `app/web/src/styles/tokens.test.ts` were not touched.

## Regression guard added

`app/web/src/components/ui/button.test.tsx` — imported `buttonVariants` alongside `Button` and added
three cases:

1. `gives lg a font-size bump, not the text-base colour utility` — calls
   `buttonVariants({ variant: 'link', size: 'lg' })` (not the bare `{ size: 'lg' }`) and asserts the
   result contains `text-[1rem]` and does not contain `text-base`. **Isolating `variant: 'link'`
   matters**: `buttonVariants`'s `defaultVariants.variant` is `'primary'`, and `primary`'s own string
   independently contains `text-base` (the deliberate colour use). An earlier draft of this test
   called `buttonVariants({ size: 'lg' })` with no variant override and asserted
   `not.toContain('text-base')` — that assertion would have failed on the *correct*, fixed code,
   because the default `primary` variant's `text-base` colour class would still be present in the
   combined output. Caught this before running vitest by reasoning through what `cva` actually
   concatenates, then confirmed by running the suite (below). Using `variant: 'link'` (which has no
   `text-base` of its own, and is the exact variant the reviewer's invisible-button scenario used)
   isolates the size-string fix from the unrelated deliberate colour use.
2. `keeps text-base as the deliberate colour pairing on the primary variant` —
   `buttonVariants({ variant: 'primary' })` contains `text-base`, pinning the 5.31:1 pair so a later
   cleanup can't silently remove it.
3. `defaults to the primary variant at the md size` — `buttonVariants()` with no args contains
   `bg-accent` and `h-11 px-6`, pinning `defaultVariants: { variant: 'primary', size: 'md' }`.

## Follow-up: the accent-fill label gets its own token (2026-09-30)

### Why the previous fix was wrong

`--color-base: #070a12` makes Tailwind v4 emit `.text-base { color: var(--color-base) }`. The token
name `base` is also Tailwind's font-size step `base`, and tailwind-merge (v3.7.0) classifies
`text-base` by name, putting it in the `font-size` group. `cn()` is `twMerge(clsx(...))`
(`app/web/src/lib/cn.ts:5`), so the primary variant's label colour and the `lg` size's
`text-[1rem]` landed in the same merge group and one of them was always dropped:

- `size="lg"` lost the colour and inherited `body { color: var(--color-text) }` = `#eef2f8` on
  `#527bff` = **3.32:1**, failing WCAG AA 4.5:1 for 16px text.
- `sm`/`md` lost `text-sm`, so every primary button rendered at 1rem instead of 0.875rem.

The old assertions could not see either, because they read `buttonVariants(...)` — the raw cva
string, before `cn()` merges it.

### Changes

- `app/web/src/styles/globals.css:21-24` — added `--color-on-accent: #070a12` to the `@theme`
  block, with a comment explaining why it duplicates `--color-base`'s value under a different name.
  No existing token value changed.
- `app/web/src/components/ui/button.tsx:13-16` — `variant.primary` now uses `text-on-accent`
  instead of `text-base`. `size.lg` keeps `text-[1rem]`.
- `app/web/src/styles/tokens.test.ts` — `on-accent` added to the list of tokens that must exist,
  plus the contrast pair `['on-accent', 'accent', 4.5, 'accent button label under its own token']`.
- `app/web/src/components/ui/button.test.tsx` — rewritten so every colour and size assertion reads
  a rendered element's `className` via `render()` + `screen.getByRole()`. The three behavioural
  cases (label, `asChild` link, disabled state) are unchanged.

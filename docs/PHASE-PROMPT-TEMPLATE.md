# Phase handoff prompt — template

This is a fill-in template for the wrapper document that hands a phase of the
McCor Labs website to a fresh Claude Code session. It is derived from
`PHASE_1_PROMPT.md`, which was composed by hand and corrected after execution;
every section below is here because phase 1 proved it was needed.

**How to use it.** Copy this file to `PHASE_<N>_PROMPT.md` at the repository
root, replace every `{{PLACEHOLDER}}`, delete the guidance blockquotes, and
delete any section that genuinely does not apply to the phase — but say in one
line why you deleted it, so a reader can tell an inapplicable section from a
forgotten one.

**What this document is not.** It is not the plan. The plan is generated by
`superpowers:writing-plans` and holds the tasks, the steps, the literal
invocations and the expected output. This wrapper carries only the things a plan
does not: the state of the working tree before task 1, the preconditions outside
the repository, what the owner should expect to see, and the exact text pasted
into the fresh session.

Read `docs/PHASE-1-CARRY-FORWARD.md` before filling this in. Several of the
sections below are answered directly by it.

## Before you start

> **Guidance.** Name the concrete commands and say what the working tree looks
> like right now. The baseline commit is not optional bookkeeping: phase 1 added
> twenty-one commits, and without a baseline there is no way to separate the
> phase's changes from work that was already uncommitted — which in phase 1
> included a concurrent session's edits to `infra/`. Also state the branch rule
> explicitly; plans do not usually say whether to branch.


## What you should expect

> **Guidance.** Set the owner's expectations so a deviation is visible. Give the
> task count and the commit count separately — they are not the same number.
> Phase 1's plan had thirteen tasks and the wrapper promised thirteen commits,
> but execution produced twenty-one, because review fix rounds land as their own
> commits whenever amending would rewrite a commit someone else has already
> built on. State that up front so extra commits do not read as a process
> failure. Also say plainly whether anything deploys, and name every step that
> needs a human.

- **{{TASK_COUNT}} tasks.** Expect {{EXPECTED_COMMIT_COUNT}} commits or more:

  task's commit.
- **{{DEPLOYMENT_STATEMENT}}** — e.g. "No deployment. No `aws` command runs at

## Steps that deliberately break things

> **Guidance.** Name them individually, by task and step number, and state the
> rule that makes them mandatory: **a rule that never fires and a hook that
> never installed are indistinguishable from passing ones.** These steps are the
> only thing that tells them apart, so an implementer under time pressure must
> not be able to read them as optional verification. Phase 1 had three, and
> every one of them caught something — the lint-rule probe confirmed the colour
> rule fired, the pre-commit probe caught that `pnpm approve-builds` alone had
> not installed the hooks, and the jsx-a11y probe added during review caught a
> plugin registration that would otherwise have silently disabled an entire
> accessibility ruleset.

Do **not** skip these:

## Definition of done

> **Guidance.** Concrete and checkable — a command and its expected result, not
> an adjective. Then state, in the same breath, every claim this phase _cannot_
> prove, because the gap is what a reader will otherwise assume away. Phase 1's
> suite proves the static export is correct and cannot prove production routing;
> saying so is the difference between an honest report and a false one.

## The prompt

> **Guidance.** This fenced block is the only part the agent reads. Keep it
> self-contained: an agent in a fresh session has no access to the surrounding
> context. It must carry the plan path, the spec path, the execution skill, the
> hard rules copied from the plan's Global Constraints _as corrected by
> execution_, the content and scope boundaries, the stop conditions, and the
> reporting framing. Copy the Global Constraints rather than citing them — phase
> 1's prompt originally paraphrased a constraint whose premises had gone stale
> and had to be corrected after the fact.
